PokoPal

A drag-and-drop tracker for which Pokémon lives in which town in Andrea's Pokopia save.

Build it.

Nothing that exists today does what Andrea described: drag a Pokémon card into the town it lives in, on a phone. The game doesn't keep a residents-per-town list either, so this fills a real gap.

The build is small. The roster and town data already exist in open community datasets, sprites come from a public Pokémon API, and the app is one web page Andrea installs to her iPhone home screen. No App Store, no developer account, no Xcode. A first working version is one working session away.

Pokopia in sixty seconds

Pokémon Pokopia is a Nintendo Switch 2 life-sim released March 5, 2026, developed by KOEI TECMO with Game Freak and published by Nintendo. You play a Ditto transformed into a human, restoring a ruined Kanto with Professor Tangrowth. You befriend Pokémon to copy their moves, reshape terrain, build habitats, and attract Pokémon to settle.

The official term is "town," and there are six today. Five in the base game, one from the Expansion Pass.

Dream Islands and Cloud Islands are not towns (resource trips and online build spaces). Some sites count seven or eight "locations" because of them.

How a Pokémon gets a home

You assemble items into one of about 250 habitat types (four Tall Grass for Bulbasaur, a Picnic Set for Pikachu). A wild Pokémon appears and that habitat becomes its home. You can also build a house, lead the Pokémon there, and ask it to move in, including into another town. Most Pokémon can live in any town. Where a Pokémon lives is Andrea's choice, so no wiki can answer it.

What the game shows you

Nothing per town. The Pokédex has a Search button that sends Ditto wandering toward the right town, and Nintendo's own patch notes admit it breaks when habitats change. Players report forgetting who was moved where. Only about 20 Pokémon render in a town at once; the rest rotate daily unless housed.

Roster today

357 numbered entries: 300 in the main dex, 50 in Bubbly Basin's own dex, 7 event Pokémon. Three sources agree on every entry. Ten alternate forms share an entry with their base Pokémon. Every one has standard Pokémon types.

What's coming

Expansion Pass Part 2 (late 2026) adds Pokémon and furniture, no town. Part 3 (2027) is planned to add a new town. The roster and the town list must be data, not fixed UI. That is the scalability requirement, and the roadmap proves it matters.

The closest tools, all web-based and free. None does drag-and-drop for Pokémon. The only drag-and-drop in this ecosystem is for furniture in town-layout planners.

Phone apps on the App Store and Google Play (Pokopedia, Pokodex, PocketDex, Poko.guide, CTA Dex, and a few companions) are all befriended checklists. None assigns a Pokémon to a town. A paid Notion database on Ko-fi tracks "homing," but it is a desktop Notion workflow.

What we reuse instead of rebuilding

  • Our own roster pull. 367 rows, the 357 entries plus the 10 alternate forms flagged as such, from Serebii, Bulbapedia and Nintendo Life, with national number, types, areas and habitat text. This is the master list.
  • kjuhwa/Pokopia on GitHub. One JSON file, generated August 30, 2026 from Serebii and PokéAPI: types, dex category, habitats with the towns each works in, rarity, time of day, weather, moods and favorites. Missing three entries (Farfetch'd, Mime Jr., Mr. Mime), so it is the detail source joined to the master list, not the roster itself.
  • JEschete/PokopiaPlanning CSV. 367 rows with per-town Yes/No flags. The cross-check.
  • PokéAPI sprites for the little pictures on each card. Verified working.
  • Serebii's Pokopia section as the canonical source if either dataset ever needs rebuilding.

Neither GitHub dataset states a license. For a private app used by two people that is fine. If this ever goes public, rebuild the data from Serebii and PokéAPI directly.

What we'll build

Named PokoPal on September 6, 2026; the working name was Pokopia Homes. The icon is Taylor's: a smiling purple book with leaf ears.

The bank

Every Pokémon not yet placed, as a compact card: sprite, name, colored by type. A search box and type filter chips at the top. A counter reads "142 of 357 placed."

The towns

Six boxes, one per town, each showing its residents and a count. On a phone they stack under the bank or swipe as a strip. Boxes fold closed when you want more of the bank.

The interaction, as Andrea described it

Press a card, drag it, drop it in a town. It stays. Drag it to another town to move it, which is also what you do in the game when you rehouse a Pokémon. Drag it back to the bank to unassign. Cards stay draggable forever, unlike Procreate. Tap-a-card-then-tap-a-town works as a fallback on tiny screens.

Saves itself, scales itself

Every drop is saved on the phone instantly. Backup exports the board as a small file; Restore loads it. Since phase 3 an account saves the board online and shares it with another person; signed out, the board still works. The roster and the town list are two data files, so the 2027 town or the Part 2 Pokémon are data edits with no code change.

Other pain points the same board can absorb later

The data file already carries these, so each is a small addition.

  • Befriended yet or not, the checklist every other app does.
  • Which house a Pokémon lives in, not just which town.
  • The habitat each Pokémon needs, with materials. Tap a card, see "Four Tall Grass."
  • Time-of-day and weather conditions for rare spawns.
  • Per-town headcount against the roughly 20-visible limit.

Technical decisions, made

A web app on the home screen, not a native app

Works on iPhone and Android, needs no App Store review or the $99-a-year developer account, updates instantly, and this Mac has no full Xcode, so a native app couldn't even be tested here. Native buys nothing for a drag-and-drop board.

Plain HTML, CSS and JavaScript, one file

Drag uses pointer events, which behave with touch on iOS Safari, unlike the browser's built-in drag-and-drop. Storage is the browser's local storage plus the backup file. A manifest and service worker make it installable and usable offline, on the couch with no signal.

Hosting on GitHub Pages, free

One-time setup: sign into GitHub on this Mac. Until then the prototype previews here in the app's browser, travels as a file, or publishes as a private Claude page.

Accounts on Firebase, free plan

The morning's version carried the board through public relays with no accounts. Taylor wants users added later, so the board needs a real sign-in, not a shared secret. Firebase Authentication does email and password with reset emails and lists every user in a console Taylor owns; Cloud Firestore holds one document per board, pushes changes to every signed-in phone live, queues offline edits, and enforces who may read or change a board through rules kept in the repo. Supabase lost on one fact: its free projects pause after a week without traffic. The board stays local-first and works signed out; the newest move per Pokémon wins when boards combine.

Testing on real glass

The browser pane here at iPhone size for layout, then Andrea's actual iPhone for the drag feel. The drag feel is the whole product; nothing is called done until it has been dragged on a phone.

Things to know

  • Pokémon names and sprites are Nintendo's property. Fine for a private tool. Don't publish it to the App Store or sell it.
  • Andrea's phone. The plan assumes iPhone. Android works the same way with Chrome.
  • Roster drift. Part 2 lands late 2026 with new Pokémon; refresh the data file when it does. Placements are keyed by Pokémon id, so a refresh never loses her board.
  • Backups. iPhone can clear a website's storage after long disuse; a home-screen install is exempt, and the Backup file covers the rest.
  • The account is the key. Email and password; a forgotten password is reset by email. An invite code lets anyone who signs in join a board and change it, so keep codes between you; New code kills the old one. Taylor's Google account owns the project and its console lists every user. The free plan allows hundreds of times what two phones use.
